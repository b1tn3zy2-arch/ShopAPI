## 2. Какие OUT-параметры и как они получались

Это главная техническая сложность работы. Всего три процедуры возвращают
OUT-параметры:

| Процедура | OUT | Использование |
|-----------|-----|---------------|
| `sp_product_add` | `p_new_id` | «Товар #5 добавлен» |
| `sp_order_create` | `p_order_id` | редирект на детали заказа |
| `sp_order_add_item` | `p_success`, `p_message` | ветвление: успех → редирект, иначе → показ `p_message` |

### Почему «как в задании» не работает

В исходном варианте `store/db.py` OUT-параметры передавались плейсхолдерами:

```python
args = list(params) + [None] * out_count
cur.execute(f"CALL {name}({placeholders})", args)
return rows, args[-out_count:] if out_count else []
```

Это даёт ошибку MySQL **1414**:

```
OUT or INOUT argument 4 for routine shop_django.sp_order_add_item
is not a variable or NEW pseudo-variable in BEFORE trigger
```

Причина: MySQL требует, чтобы на месте `OUT`/`INOUT`-параметра стояла
**переменная**, а не литерал и не плейсхолдер `?` подготовленного запроса.
Дополнительно `cursor.execute()` не возвращает изменённые OUT-значения в
список `args`, поэтому даже без ошибки 1414 срез `args[-out_count:]` вернул бы
исходные заглушки, а не результат.

`cursor.callproc()` из MySQLdb проблему не решает — он формирует ту же строку
`CALL ...(%s, %s)`.

### Рабочее решение

Для каждого OUT-параметра заводится **сессионная переменная** `@_out_N`, её
значение читается отдельным `SELECT` сразу после вызова (`store/db.py`):

```python
params = list(params)
out_vars = [f'@_out_{i}' for i in range(out_count)]
placeholders = ','.join(['%s'] * len(params) + out_vars)
sql = f"CALL {name}({placeholders})"

with connection.cursor() as cur:
    cur.execute(sql, params)
    rows = cur.fetchall() if fetch else None

    while cur.nextset():      # дочитываем служебные наборы результатов
        pass

    out_values = []
    if out_count:
        cur.execute('SELECT ' + ','.join(out_vars))
        row = cur.fetchone()
        out_values = list(row) if row else []
```

`CALL sp_product_add('Планшет', 1, 19990.00, 10, @_out_0)`, затем
`SELECT @_out_0` → `5`.

Проверенные значения:

```
sp_product_add   OUT p_new_id     -> [5]
sp_order_create  OUT p_order_id   -> [3]
sp_order_add_item OUT p_success   -> [1]                 (успех)
sp_order_add_item OUT p_message   -> 'Недостаточно товара. Доступно: 2'
sp_order_add_item OUT p_message   -> 'Товар не найден'
sp_order_add_item OUT p_message   -> 'Количество должно быть больше нуля'
```

## 3. Как обрабатывались ошибки

Задание 8. Реализация в `store/db.py` + декоратор `@handle_db_errors`
на каждом view.

**Цепочка обработки:**

1. `DatabaseError` перехватывается в обёртке.
2. Выполняется откат (`ROLLBACK`), чтобы соединение не осталось в
   «зависшей» транзакции.
3. Полный `traceback.format_exc()` пишется в `logs/db_errors.log`.
4. Код errno MySQL переводится в человекочитаемый текст (`ERROR_HINTS`).
5. Бросается `StoredProcedureError` — доменное исключение без деталей БД.
6. Декоратор ловит его и показывает `messages.error`, редиректя на
   `products_list`. Пользователь видит текст, а не traceback.

Там же перехватываются `KeyError/ValueError/TypeError` — мусор в форме
(`quantity=abc`) даёт «Проверьте правильность заполнения полей формы»
вместо 500.

**Проверенные сценарии:**

| Сценарий | errno | Сообщение пользователю |
|----------|-------|------------------------|
| Несуществующая процедура | 1305 | `Не удалось выполнить sp_nope: Хранимая процедура не найдена: проверьте sql/procedures.sql` |
| Несуществующая функция | 1305 | `Не удалось вычислить fn_nope: Хранимая функция не найдена: проверьте sql/functions.sql` |
| Неверное число параметров | 1318 | `Неверное число OUT-параметров у процедуры` |
| Нарушение FK | 1452 | `Нарушение внешнего ключа: проверьте, что категория/клиент/товар существует` |

Отдельно отмечу: ошибка **1414** в логе не появляется — она устранена
конструкцией с `@_out_N`.

Ошибки, которые процедура обрабатывает **сама** (через OUT, без исключения),
показаны пользователю напрямую: «Недостаточно товара. Доступно: 2».

## 4. Что было сложным

1. **OUT-параметры (главное).** Ошибка 1414 не гуглится легко: формально
   запрос выглядит правильно, `?`-плейсхолдеры кажутся логичными. Пришлось
   проверить три варианта (`execute` + срез `args`, `callproc`,
   сессионные переменные) и сравнить результат. Победил вариант с `@_out_N`.

2. **Пропущенный `load_dotenv()`.** В `settings.py` был только
   `from dotenv import load_dotenv` без вызова. `os.getenv('DB_*')` молча
   возвращал `None`, Django подставлял имя пользователя ОС, и MySQL отвечал
   `Access denied ... using password: NO` — ошибка маскировала реальную
   причину.

3. **Шаблоны вне области видимости Django.** Каталог `templates/store/`
   находился в корне проекта, а `TEMPLATES['DIRS']` был пустым — Django
   искал шаблоны только в `<app>/templates/` и в библиотеках. Решено
   размещением шаблонов в `store/templates/store/`.

4. **Имя файла без расширения.** Шаблон лежал как `templates/store/products_list`
   (без `.html`), тогда как view рендерит `store/products_list.html`.

5. **`sql_mode`.** Добавлен `init_command` с `STRICT_TRANS_TABLES` — иначе
   MySQL молча усекает неверные значения вместо ошибки.

## 5. Ответы на контрольные вопросы

**1. Почему бизнес-логику вынесли в MySQL, а не оставили в Django?**
Чтобы вся логика продаж выполнялась в одном месте независимо от языка
клиента: консоль, отчёт, веб-приложение или микросервис дадут одинаковый
результат. Плюс MySQL выполняет её рядом с данными, без перекачки строк
в Python, и может задействовать индексы, кэш и транзакции на уровне сервера.

**2. Разница между `call_procedure` и `call_function`?**
`call_procedure` выполняет `CALL`, может вернуть набор строк **и** OUT-значения,
поэтому возвращает кортеж `(rows, out_values)`. `call_function` выполняет
`SELECT func(...)` — функция обязана вернуть скаляр, поэтому возвращается
только это значение. Функции в MySQL не могут менять данные, процедуры — могут.

**3. Как получить значение OUT-параметра после вызова?**
Передать на его место сессионную переменную `@_out_N`, после `CALL` выполнить
`SELECT @_out_N`. Плейсхолдер `?` для OUT недопустим (ошибка 1414).

**4. Что произойдёт, если процедура выбросит исключение и мы не сделаем ROLLBACK?**
Транзакция останется открытой: соединение будет удерживать блокировки
(`FOR UPDATE`) до конца сессии, другие транзакции будут ждать или получать
блокировку, а частично применённые изменения (запись в `order_items` без
списания остатка) могут быть закоммичены позже случайно. В `sp_order_add_item`
поэтому есть `DECLARE EXIT HANDLER FOR SQLEXCEPTION`, который делает
`ROLLBACK` и заполняет `p_success`/`p_message`.

**5. Почему важен `SELECT ... FOR UPDATE` при списании товара?**
Без него два параллельных заказа читают один и тот же `stock`, оба видят
«хватает», оба вставляют позицию — товар списывается дважды и уходит в
минус. `FOR UPDATE` блокирует строку товара до конца транзакции, поэтому
второй заказ ждёт и читает уже обновлённый остаток.

**6. Преимущества `EXIT HANDLER`?**
Позволяет не дублировать обработку в каждом месте: одно объявление перехватывает
любую ошибку (`SQLEXCEPTION`), гарантирует `ROLLBACK` и возвращает ошибку
через OUT-параметры вместо SQL-исключения. Процедура не падает, а сообщает
результат в контролируемом виде — Python получает обычные значения.

**7. Зачем `charset='utf8mb4` в настройках подключения?**
`utf8mb4` — единственная кодировка MySQL, поддерживающая 4 байта на символ,
то есть весь Unicode, включая эмодзи. Старый `utf8mb3` умеет только 3 байта
и ломает такие символы. Без неё русские тексты в товарах и сообщения
процедур приходят в виде «Ð¡Ð¼Ð°Ñ€Ñ‚Ñ„Ð¾Ð½».

**8. Как проверить, что используется процедура, а не обычный SQL?**
Включить лог запросов и посмотреть на префикс:

```sql
SET GLOBAL general_log = 'ON';
SET GLOBAL log_output = 'TABLE';
SELECT * FROM mysql.general_log;
```

В логе будут строки вида `CALL sp_products_list ()` и
`SELECT fn_customer_discount(1, 20000)`. Также это видно в
`information_schema.ROUTINES` (16 объектов) и в `SHOW PROCEDURE STATUS`.
Отдельно: `store/models.py` пуст — ни одной ORM-модели нет, значит
операций типа `SELECT ... FROM products` из Python не происходит.
